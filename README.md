# Traffic Object Detection: подготовка датасета и эксперимент с YOLOv8

## 1. Описание проекта

Проект посвящён подготовке и проверке датасета для задачи обнаружения объектов дорожного движения, а также организации воспроизводимого эксперимента с использованием YOLOv8n.

Основное внимание уделено инженерной части задачи:

- проверке и исправлению аннотаций;
- подготовке датасета в формате YOLO;
- разделению данных на обучающую, валидационную и тестовую выборки;
- проверке корректности структуры данных;
- настройке и запуску экспериментов;
- сохранению конфигураций, метрик и журналов обучения;
- визуализации результатов с помощью TensorBoard;
- автоматизированной проверке вспомогательных компонентов проекта.

Качество модели также оценивается, однако из-за небольшого размера датасета и сильного дисбаланса классов полученные метрики не следует считать надёжной оценкой качества на реальных дорожных сценах.

### Какие данные включаются в репозиторий

В Git включаются две версии мини-датасета:

- `test_data/traffic_v5_mini/` — исходная мини-выборка из задания, сохранённая без изменений для возможности сравнения с оригиналом;
- `data/raw/traffic_mini_corrected/` — отдельная исправленная копия, используемая в качестве источника для воспроизводимой подготовки данных.

Исправленный датасет публикуется вместе с кодом подготовки, чтобы можно было повторно выполнить проверку данных и сформировать разбиение на train, val и test.

Каталог `data/processed/` не включается в Git: он генерируется скриптом `src/prepare_dataset.py` из `data/raw/traffic_mini_corrected/`. Это позволяет не хранить в репозитории дополнительные копии изображений и аннотаций.

Сгенерированные визуализации в `reports/samples/visualizations/` также остаются локально: их можно повторно создать при подготовке датасета. Основной отчёт `reports/dataset_report.md` и манифест `reports/manifest.sha256` включаются в репозиторий как компактные артефакты проверки.

Веса моделей, кэши, журналы TensorBoard и результаты запусков из `runs/` не включаются в Git, поскольку они создаются локально и могут занимать значительный объём.


## 3. Датасет

В работе используются 11 классов объектов:

1. `bicycle`
2. `car`
3. `motorcycle`
4. `bus`
5. `truck`
6. `lorry`
7. `trailer`
8. `police`
9. `ambulance`
10. `fire_truck`
11. `pedestrian`

Аннотации представлены в формате Ultralytics YOLO Detection:

```text
class_id x_center y_center width height
```

Координаты центра, ширина и высота рамки нормализованы относительно размеров изображения.

### Подготовка данных

Исходный датасет был проверен, а обнаруженные проблемы с аннотациями исправлены в отдельной рабочей копии. Исходные данные задания при этом сохранены отдельно от исправленной версии.

Для воспроизводимости исправленная копия data/raw/traffic_mini_corrected/ включена в репозиторий, тогда как итоговое разбиение в data/processed/ создаётся скриптом и не хранится в Git.

Подготовленный датасет содержит:

| Показатель | Значение |
|---|---:|
| Изображения | 40 |
| Файлы аннотаций | 40 |
| Размеченные объекты | 920 |
| Классы | 11 |
| Обучающая выборка | 28 изображений |
| Валидационная выборка | 6 изображений |
| Тестовая выборка | 6 изображений |

При проверке структуры не обнаружено отсутствующих файлов аннотаций, лишних файлов разметки или структурных ошибок в проверенных YOLO-аннотациях.

Техническая проверка формата сама по себе не гарантирует семантическую правильность каждой рамки. Поэтому дополнительно проводилась визуальная проверка и корректировка разметки.

### Ограничения датасета

Датасет очень мал, а распределение объектов по классам сильно неравномерно. Например, класс `car` представлен значительно большим числом объектов, чем `bicycle` или `lorry`.

Это может приводить к тому, что модель преимущественно обучается на частых классах и плохо обнаруживает редкие. Кроме того, валидационная выборка состоит всего из шести изображений, поэтому метрики могут существенно меняться даже при небольших изменениях эксперимента.

В нём могут присутствовать локальные абсолютные пути, поэтому этот файл следует рассматривать как артефакт конкретного запуска, а не универсальную конфигурацию для другой машины.

## 7. Dry-run: проверка запуска без обучения

Перед запуском эксперимента необходимо подготовить датасет командой python -m src.prepare_dataset. После успешного завершения скрипта конфигурация YOLO будет доступна по пути data/processed/dataset.yaml.

Перед фактическим обучением был выполнен dry-run:

```bash
python -m src.run_experiment \
  --config configs/yolo.yaml \
  --data data/processed/dataset.yaml \
  --dry-run
```

Dry-run предназначен для предварительной проверки сценария эксперимента без запуска обучения модели.

В рамках такого запуска создаётся каталог эксперимента и сохраняются конфигурация и метаданные. При этом обучение не начинается, веса модели не обучаются, а файлы `best.pt` и `last.pt` не создаются.

### Результат dry-run

Dry-run завершился успешно: в метаданных локального запуска был зафиксирован статус `dry_run_passed`. Этот этап позволил проверить подготовительную часть эксперимента и создание служебных артефактов без обучения модели. Результаты запуска сохраняются локально и не публикуются в GitHub.

## 9. TensorBoard: просмотр логов обучения

Для просмотра журналов экспериментов используется TensorBoard:

```bash

```

После запуска TensorBoard выведет локальный адрес, который можно открыть в браузере.

Если команда `tensorboard` недоступна в активном окружении, можно попробовать альтернативный запуск:

```bash

```

### Два типа event-файлов

В каталоге эксперимента могут присутствовать два типа файлов событий:

```text
tensorboard/events.out.tfevents.*
ultralytics/events.out.tfevents.*
```

Они создаются разными логгерами:

- `tensorboard/events.out.tfevents.*` — события, записанные собственным логгером проекта из `src/tensorboard_logger.py`;
- `ultralytics/events.out.tfevents.*` — события, записанные встроенным механизмом логирования Ultralytics во время обучения.

Это отдельные потоки событий, а не обязательно дубли одного и того же файла. Они могут содержать пересекающиеся показатели, но наборы тегов и расписание записи зависят от соответствующего логгера.

TensorBoard может читать оба типа событий. Если в каталоге есть оба файла, это не означает, что один из них лишний или повреждён.

При dry-run собственный логгер может создать event-файл, хотя обучение не запускалось. Поэтому наличие event-файла само по себе не подтверждает, что модель обучалась.

Event-файлы являются журналами конкретных запусков. Они относятся к локальным артефактам экспериментов и не включаются в итоговый состав проекта.

В рамках работы были выполнены следующие этапы:

- подготовлена отдельная исправленная версия исходного датасета;
- проверена структура изображений и YOLO-аннотаций;
- сформированы обучающая, валидационная и тестовая выборки;
- реализованы вспомогательные скрипты подготовки и проверки данных;
- добавлены автоматизированные тесты;

Основное ограничение — размер датасета: всего 40 изображений при 11 классах и существенном дисбалансе объектов. Поэтому результаты обучения нельзя считать убедительным доказательством качества детектора на новых данных.

Ценность эксперимента заключается не только в полученных метриках, но и в организации воспроизводимого процесса: от подготовки и проверки данных до запуска обучения, сохранения параметров и анализа результатов.

Для дальнейшего повышения качества модели потребовались бы более крупный и сбалансированный датасет, дополнительная проверка качества аннотаций и новые эксперименты с настройками обучения.
