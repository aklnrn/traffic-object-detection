# Traffic Object Detection: подготовка датасета и эксперимент с YOLOv8

## 1. Описание проекта

Проект посвящён подготовке и проверке датасета для задачи обнаружения объектов дорожного движения, а также организации воспроизводимого эксперимента с использованием YOLOv8n.

Основное внимание уделено инженерной части задачи:

- проверке и исправлению аннотаций;
- подготовке датасета в формате Ultralytics YOLO Detection;
- разделению данных на обучающую, валидационную и тестовую выборки;
- проверке корректности структуры данных и формата аннотаций;
- созданию отчёта о датасете и SHA-256-манифеста;
- визуализации bounding boxes для ручной проверки разметки;
- настройке и запуску экспериментов;
- сохранению конфигураций, метрик и журналов обучения;
- визуализации результатов с помощью TensorBoard;
- автоматизированной проверке вспомогательных компонентов проекта.

Качество модели также оценивается, однако из-за небольшого размера датасета и сильного дисбаланса классов полученные метрики не следует считать надёжной оценкой качества на реальных дорожных сценах.

- `data/raw/traffic_mini_corrected/` — отдельная исправленная копия исходных данных, используемая для повторной подготовки датасета.
- `data/processed/` — готовый датасет с разбиением на train, val и test, включённый в репозиторий.
- `configs/yolo.yaml` — параметры эксперимента и обучения.
- `src/` — скрипты подготовки данных, проверки аннотаций, запуска экспериментов и логирования.
- `tests/` — автоматизированные тесты.
- `reports/` — отчёт о датасете, контрольные суммы, визуализации разметки и опубликованные артефакты экспериментов.
- `runs/` — локальные результаты новых запусков, включая конфигурации, графики, журналы и веса модели, если они были сохранены.

**Примечания:**

- Предобученные веса `yolov8n.pt` загружаются локально при необходимости и не включены в репозиторий.
- В `reports/experiments/` опубликованы выбранные артефакты ранее выполненных экспериментов. Веса моделей `.pt` и `.pth` не публикуются.
- Готовый датасет `data/processed/` и визуализации разметки `reports/samples/visualizations/` уже включены в репозиторий.
- Полное содержимое `runs/` не публикуется автоматически. При запуске экспериментов новые артефакты сохраняются локально.


## 3. Датасет

В проекте используются 11 классов объектов:

| ID | Класс |
|---:|---|
| 0 | `bicycle` |
| 1 | `car` |
| 2 | `motorcycle` |
| 3 | `bus` |
| 4 | `truck` |
| 5 | `lorry` |
| 6 | `trailer` |
| 7 | `police` |
| 8 | `ambulance` |
| 9 | `fire_truck` |
| 10 | `pedestrian` |

Аннотации представлены в формате Ultralytics YOLO Detection:

```text
class_id x_center y_center width height
```

Каждая строка описывает один объект. `class_id` — индекс класса, а `x_center`, `y_center`, `width` и `height` — нормализованные координаты центра, ширина и высота ограничивающей рамки относительно размеров изображения.

### 3.1. Характеристики датасета

Подготовленный датасет содержит:

| Показатель | Значение |
|---|---:|
| Изображения | 40 |
| Файлы аннотаций | 40 |
| Размеченные объекты | 920 |
| Классы | 11 |
| Обучающая выборка (train) | 28 изображений |
| Валидационная выборка (val) | 6 изображений |
| Тестовая выборка (test) | 6 изображений |

При проверке структуры и аннотаций выполняется контроль наличия изображений и соответствующих файлов разметки, допустимости идентификаторов классов и корректности нормализованных координат.

Техническая проверка формата сама по себе не гарантирует семантическую правильность каждой рамки. Поэтому визуализации bounding boxes используются дополнительно для ручной проверки и оценки качества разметки.

### 3.2. Ограничения датасета

Датасет небольшой, а распределение объектов по классам сильно неравномерно. Например, класс `car` представлен значительно большим количеством объектов, чем `bicycle` или `lorry`.

Это может приводить к тому, что модель лучше обнаруживает частые классы и хуже справляется с редкими. Кроме того, валидационная и тестовая выборки состоят всего из шести изображений каждая, поэтому метрики могут существенно меняться даже при небольших изменениях эксперимента.

## 4. Окружение и установка

Для проекта использовались Python 3.11.9, Ultralytics 8.3.0, PyTorch 2.6.0 и TensorBoard 2.19.0.

Рекомендуется использовать Python 3.11 и отдельное виртуальное окружение.

### 4.1. Клонирование репозитория

Установите Git и Python 3.11, затем выполните:

```bash
git clone https://github.com/aklnrn/traffic-object-detection.git

cd traffic-object-detection
```

Все последующие команды необходимо выполнять из корневого каталога проекта.

### 4.2. Создание виртуального окружения

**macOS / Linux**

```bash
python3.11 -m venv .venv

source .venv/bin/activate
```

**Windows PowerShell**

```powershell
py -3.11 -m venv .venv

.\.venv\Scripts\Activate.ps1
```

Если PowerShell запрещает активацию скриптов, можно использовать командную строку Windows:

```bat
.venv\Scripts\activate.bat
```

### 4.3. Установка зависимостей

Обновите `pip` и установите зависимости проекта:

```bash
python -m pip install --upgrade pip

python -m pip install -r requirements.txt
```

В `requirements.txt` зафиксированы версии основных библиотек, включая PyTorch, Ultralytics, OpenCV, Pillow, PyYAML, TensorBoard и pytest.

Для установки PyTorch может потребоваться дополнительное время и свободное место на диске.

### 4.4. Проверка окружения

Убедитесь, что используется ожидаемая версия Python:

```bash
python --version
```

Проверьте доступность основных библиотек:

```bash
python -c "import ultralytics, torch, tensorboard, yaml; print('Ultralytics:', ultralytics.__version__); print('PyTorch:', torch.__version__); print('TensorBoard:', tensorboard.__version__)"
```

Команды запуска проекта необходимо выполнять с активированным виртуальным окружением.

## 5. Подготовка датасета

В репозитории доступны два варианта работы с данными:

1. **Использовать готовый датасет** из `data/processed/`. Этот вариант подходит для быстрого запуска обучения и не требует повторной подготовки данных.
2. **Самостоятельно подготовить датасет** из исходных данных. Скрипт проверит структуру и аннотации, сформирует разбиение train/val/test, создаст конфигурацию YOLO, отчёт, SHA-256-манифест и визуализации bounding boxes.

### 5.1. Вариант A — использовать готовый датасет

Подготовленный датасет уже включён в репозиторий:

```text
data/processed/
├── dataset.yaml
├── images/
│   ├── train/
│   ├── val/
│   └── test/
└── labels/
    ├── train/
    ├── val/
    └── test/
```

В нём 40 изображений: 28 для обучения, 6 для валидации и 6 для тестирования. Конфигурация `dataset.yaml` содержит пути к выборкам и названия 11 классов.

Чтобы проверить, что файлы на месте, выполните из корня проекта:

```bash
ls data/processed

ls data/processed/images

ls data/processed/labels
```

Дополнительно можно проверить чтение YAML и содержимое конфигурации:

```bash
python -c "import yaml; d=yaml.safe_load(open('data/processed/dataset.yaml', encoding='utf-8')); print('Классов:', len(d['names'])); print('Train:', d['train']); print('Val:', d['val']); print('Test:', d['test'])"
```

Ожидается 11 классов и пути `images/train`, `images/val`, `images/test`.

**Для обычного запуска обучения используйте `data/processed/dataset.yaml` и переходите к разделу 8.** Повторно подготавливать датасет не требуется.

### 5.2. Вариант B — самостоятельно подготовить датасет

Этот сценарий позволяет повторно выполнить подготовку данных из исправленной исходной копии, включённой в репозиторий:

```text
data/raw/traffic_mini_corrected/
├── classes.txt
├── images/
└── labels/
```

Перед запуском убедитесь, что виртуальное окружение активировано и зависимости установлены.

#### Шаг 1. Посмотреть параметры скрипта

```bash
python -m src.prepare_dataset --help
```

Скрипт `src/prepare_dataset.py` проверяет изображения и YOLO-аннотации, формирует разбиение данных и создаёт необходимые артефакты.

#### Шаг 2. Запустить подготовку датасета

Если нужно сформировать датасет в стандартном каталоге проекта, команда выглядит так:

```bash
python -m src.prepare_dataset
```

По умолчанию используются следующие пути:

| Назначение | Путь |
|---|---|
| Исходные изображения | `data/raw/traffic_mini_corrected/images/` |
| Исходные аннотации | `data/raw/traffic_mini_corrected/labels/` |
| Список классов | `data/raw/traffic_mini_corrected/classes.txt` |
| Подготовленный датасет | `data/processed/` |
| Отчёт о датасете | `reports/dataset_report.md` |
| SHA-256-манифест | `reports/manifest.sha256` |
| Визуализации разметки | `reports/samples/visualizations/` |

Скрипт использует фиксированный `seed=42` по умолчанию. Для данного проекта ожидается 40 изображений, которые распределяются между выборками в пропорции 70/15/15:

- train — 28 изображений;
- val — 6 изображений;
- test — 6 изображений.

При разбиении связанные изображения не должны попадать в разные выборки.

**Важно:** каталог `data/processed/` уже существует и содержит опубликованный датасет. Скрипт не перезаписывает непустой каталог выходных данных, поэтому повторный запуск команды с настройками по умолчанию может завершиться ошибкой. Не удаляйте опубликованный датасет ради повторного запуска.

Для проверочной подготовки рекомендуется использовать отдельные пути для всех выходных артефактов:

```bash
python -m src.prepare_dataset \
  --output data/processed_recheck \
  --report reports/dataset_report_recheck.md \
  --manifest reports/manifest_recheck.sha256 \
  --visualizations reports/samples/visualizations_recheck
```

Такой запуск создаст отдельную копию подготовленного датасета и не затронет опубликованные файлы в `data/processed/`.

#### Шаг 3. Проверить результат подготовки

После завершения скрипт выведет количество изображений и объектов в каждой выборке, пути к созданным файлам и количество визуализаций.

Проверьте структуру нового датасета:

```bash
ls data/processed_recheck

ls data/processed_recheck/images

ls data/processed_recheck/labels
```

Ожидаемая структура:

```text
data/processed_recheck/
├── dataset.yaml
├── images/
│   ├── train/
│   ├── val/
│   └── test/
└── labels/
    ├── train/
    ├── val/
    └── test/
```

Проверьте сформированный отчёт:

```bash
cat reports/dataset_report_recheck.md
```

Отчёт содержит статистику датасета и распределение объектов по классам и выборкам.

Файл `reports/manifest_recheck.sha256` содержит контрольные суммы SHA-256 для файлов подготовленного датасета. Он позволяет проверить, изменились ли файлы после формирования манифеста.

#### Шаг 4. Посмотреть визуализации bounding boxes

Скрипт создаёт визуализацию для каждого исходного изображения: на изображение наносятся ограничивающие рамки и метки классов.

При использовании команды с отдельными путями визуализации находятся в:

```text
reports/samples/visualizations_recheck/
```

Посмотреть список файлов можно командой:

```bash
ls reports/samples/visualizations_recheck
```

Откройте изображения в файловом менеджере или редакторе изображений и проверьте:

- соответствуют ли рамки реальным объектам;
- охватывают ли рамки нужные объекты;
- правильно ли отображаются названия классов;
- нет ли очевидных ошибок или пропущенных объектов.

В стандартном режиме визуализации создаются в `reports/samples/visualizations/`. Для повторной проверки рекомендуется использовать отдельный каталог, чтобы не смешивать результаты с опубликованными визуализациями.

#### Шаг 5. Проверить аннотации и автоматизированные тесты

Для просмотра параметров валидатора:

```bash
python -m src.validate_labels --help
```

Для запуска автоматизированных тестов:

```bash
python -m pytest tests/ -v
```

Тесты проверяют корректность формата аннотаций и логику разбиения данных. Они дополняют визуальную проверку, но не заменяют её: корректный формат координат сам по себе не гарантирует, что каждая рамка семантически правильно охватывает объект.

#### Шаг 6. Проверить подготовленный датасет перед обучением

После подготовки можно выполнить проверку эксперимента без обучения. Для проверочной копии используйте:

```bash
python -m src.run_experiment \
  --config configs/yolo.yaml \
  --data data/processed_recheck/dataset.yaml \
  --dry-run
```

Если проверка завершилась успешно, для обучения уберите аргумент `--dry-run`:

```bash
python -m src.run_experiment \
  --config configs/yolo.yaml \
  --data data/processed_recheck/dataset.yaml
```

Для обычного запуска на опубликованном датасете используйте `data/processed/dataset.yaml`, как описано в разделе 8.


В проверенном окружении проекта успешно прошли **17 тестов**.

Тесты охватывают проверку YOLO-аннотаций и логику разбиения датасета. Успешное прохождение тестов помогает убедиться, что основные вспомогательные компоненты работают ожидаемым образом, но не заменяет визуальную проверку качества разметки.

## 7. Конфигурация эксперимента

Основные параметры эксперимента находятся в `configs/yolo.yaml`.

В конфигурации заданы следующие параметры:

| Параметр | Значение |
|---|---|
| Модель | YOLOv8n |
| Предобученные веса | `yolov8n.pt` |
| Количество эпох | 30 |
| Размер изображения | 320 × 320 |
| Batch size | 2 |
| Устройство | CPU |
| Число workers | 0 |
| Seed | 42 |
| Deterministic mode | Включён |
| AMP | Выключен |
| Optimizer | `auto` |
| Patience | 10 |
| Валидация во время обучения | Включена |

Параметры подобраны с учётом ограниченных вычислительных ресурсов. Обучение проводится на CPU, поэтому небольшой размер изображений и batch size позволяют снизить вычислительную нагрузку.

Файл `data/processed/dataset.yaml` описывает расположение выборок и список классов. При запуске Ultralytics также может сохранять в каталоге эксперимента файл `ultralytics_dataset.yaml` с конфигурацией конкретного запуска. В нём могут присутствовать локальные абсолютные пути, поэтому этот файл следует рассматривать как артефакт отдельного запуска, а не универсальную конфигурацию для другой машины.

## 8. Dry-run: проверка запуска без обучения

Перед фактическим обучением рекомендуется проверить доступность данных и загрузку модели.

Для готового датасета выполните:

```bash
python -m src.run_experiment \
  --config configs/yolo.yaml \
  --data data/processed/dataset.yaml \
  --dry-run
```

Параметр `--dry-run` запускает предварительную проверку без обучения модели.

В этом режиме скрипт проверяет подготовку эксперимента, обрабатывает конфигурацию и данные, сообщает количество изображений в выборках и вычисляет контрольный хеш датасета. Также создаётся каталог запуска со служебными конфигурациями и метаданными.

При этом обучение не начинается, а новые обученные веса `best.pt` и `last.pt` не создаются.

Dry-run был успешно выполнен в проверенном окружении проекта. Результаты опубликованной проверки находятся в `reports/experiments/yolov8n_cpu_dry_run_config_check/`.

## 9. Запуск обучения YOLOv8n

Для запуска эксперимента с параметрами из `configs/yolo.yaml` выполните:

```bash
python -m src.run_experiment \
  --config configs/yolo.yaml \
  --data data/processed/dataset.yaml
```

При необходимости можно переопределить количество эпох, например для короткого проверочного обучения:

```bash
python -m src.run_experiment \
  --config configs/yolo.yaml \
  --data data/processed/dataset.yaml \
  --epochs 3
```

Используется предобученная модель `yolov8n.pt`. Если её весов нет локально, Ultralytics обычно загружает их автоматически, поэтому при первом запуске потребуется доступ к интернету.

**Количество 30 эпох — это заданный верхний предел, а не гарантия того, что обучение завершится именно на 30-й эпохе.** При включённой ранней остановке обучение может завершиться раньше, если контролируемая метрика не улучшается в течение заданного числа эпох.

Скрипт создаёт отдельный каталог эксперимента в `runs/` с уникальным именем. В нём сохраняются конфигурация запуска и формируемые артефакты. Предыдущие запуски не должны перезаписываться.

Полноценное обучение запускает вычисления и может занять заметное время на CPU. Команда выше предназначена для реального запуска обучения, а не для проверки конфигурации.

## 10. Результаты

После завершения обучения проверьте созданный каталог внутри `runs/`. В зависимости от этапа и настроек запуска там могут находиться:

- `results.csv` — метрики по эпохам;
- `results.png` — графики обучения;
- `confusion_matrix.png` и `confusion_matrix_normalized.png` — матрицы ошибок;
- `P_curve.png`, `R_curve.png`, `F1_curve.png`, `PR_curve.png` — графики метрик;
- `train_batch*.jpg` — примеры обучающих изображений;
- `val_batch*_labels.jpg` и `val_batch*_pred.jpg` — сравнение исходной разметки и предсказаний;
- конфигурации эксперимента и журналы TensorBoard;
- контрольные точки модели, если они были сохранены.

Фактический набор файлов зависит от запуска. Если используется ранняя остановка, количество записей в `results.csv` может быть меньше заданного числа эпох.

### 10.1. TensorBoard: просмотр логов обучения

Для просмотра журналов экспериментов используется TensorBoard. Чтобы посмотреть логи конкретного запуска, укажите его каталог:

```bash
tensorboard --logdir runs/ИМЯ_КАТАЛОГА/tensorboard
```

Замените `ИМЯ_КАТАЛОГА` на имя созданного каталога эксперимента. Затем откройте локальный адрес, который TensorBoard выведет в терминале, в браузере.

Если нужно просмотреть журналы нескольких запусков, можно указать общий каталог:

```bash
tensorboard --logdir runs
```

Если команда `tensorboard` недоступна в активном окружении, попробуйте:

```bash
python -m tensorboard.main --logdir runs
```

#### Два типа event-файлов

В каталоге эксперимента могут присутствовать два типа файлов событий:

```text
tensorboard/events.out.tfevents.*
ultralytics/events.out.tfevents.*
```

Они создаются разными логгерами:

- `tensorboard/events.out.tfevents.*` — события, записанные собственным логгером проекта из `src/tensorboard_logger.py`;
- `ultralytics/events.out.tfevents.*` — события, записанные встроенным механизмом логирования Ultralytics во время обучения.

Это отдельные потоки событий, а не обязательно дубли одного и того же файла. Они могут содержать пересекающиеся показатели, но набор тегов и расписание записи зависят от соответствующего логгера.

TensorBoard может читать оба типа событий. Если в каталоге есть оба файла, это не означает, что один из них лишний или повреждён.

При dry-run собственный логгер может создать event-файл, хотя обучение не запускалось. Поэтому наличие event-файла само по себе не подтверждает, что модель обучалась.

### 11.2. Короткое обучение на трёх эпохах

Короткий запуск использовался для проверки полного цикла обучения: загрузки датасета, запуска модели, расчёта метрик и сохранения результатов.

Результаты короткого запуска следует рассматривать прежде всего как подтверждение работоспособности конвейера, а не как доказательство высокого качества модели.

### 11.3. Эксперимент с настройкой на 30 эпох

В конфигурации расширенного эксперимента был установлен лимит в 30 эпох, однако в сохранённом `results.csv` присутствуют записи только за 15 эпох.

Лучший checkpoint был получен на 5-й эпохе, а последняя сохранённая эпоха — 15-я. Эти показатели описывают разные состояния модели: метрики последней эпохи не следует автоматически считать метриками лучшего checkpoint.

Артефакты этого запуска рассматриваются как результаты конкретного исторического эксперимента, а не как гарантия завершения обучения на 30 эпохах.

Веса моделей не включены в репозиторий. Новые запуски создают локальные артефакты в `runs/`, которые не публикуются автоматически.

## 12. Ограничения и выводы

В рамках работы были выполнены следующие этапы:

- подготовлена отдельная исправленная версия исходного датасета;
- проверены структура изображений и YOLO-аннотации;
- сформированы обучающая, валидационная и тестовая выборки;
- реализованы вспомогательные скрипты подготовки и проверки данных;
- созданы отчёт, SHA-256-манифест и визуализации bounding boxes;
- добавлены автоматизированные тесты;
- выполнен dry-run для проверки подготовительного этапа;
- проведено короткое обучение на трёх эпохах;

Дополнительное ограничение связано с размером валидационной и тестовой выборок: шесть изображений в каждой недостаточны для устойчивой оценки обобщающей способности модели.

Ценность эксперимента заключается не только в полученных метриках, но и в организации воспроизводимого процесса: от подготовки и проверки данных до запуска обучения, сохранения параметров и анализа результатов.

Для дальнейшего повышения качества модели потребовались бы более крупный и сбалансированный датасет, дополнительная проверка качества аннотаций и новые эксперименты с настройками обучения.
